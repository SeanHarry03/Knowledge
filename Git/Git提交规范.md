# Git 提交规范

适用于游戏客户端、服务端、资源与工具开发。每次提交只表达一个明确目的，便于代码审查、问题追踪和回退。

## 1. 标准提交格式

```text
<type>(<scope>): <中文简述>

<修改原因、处理方式、影响范围；简单改动可省略>

Zentao-Bug: <禅道 Bug 编号>
Bug-Type: <Bug 分类>
Module: <业务模块路径>
Test: <验证环境、步骤与实际结果>
```

- 标题必须包含 `type`、`scope` 和简述；使用英文括号、英文冒号，冒号后留一个空格。
- 简述写清“改了什么”，建议标题不超过 72 个字符，不写“修改 Bug”“更新代码”等模糊描述。
- 标题、正文、末尾字段块之间各空一行；字段块内部不空行，每个字段单独一行。
- 字段按模板顺序填写；不适用的可选字段直接省略，不填写空值或虚构编号。
- 本文定义团队提交约定；自动关联、回写禅道需另行配置工具，填写字段本身不会改变 Bug 状态。

## 2. type 规范

| type | 用途 | 游戏开发示例 |
| --- | --- | --- |
| `fix` | 修复已确认的缺陷 | 修复断线重连后重复扣除体力 |
| `feat` | 新增功能或玩法 | 新增背包道具批量出售功能 |
| `perf` | 主动性能优化 | 减少战斗中临时对象分配 |
| `refactor` | 重构，不改变外部行为 | 拆分技能结算逻辑 |
| `test` | 新增或调整测试 | 补充掉落概率边界测试 |
| `docs` | 文档修改 | 更新战斗协议说明 |
| `style` | 代码格式调整，不改变逻辑 | 统一缩进和格式 |
| `build` | 构建、打包、依赖调整 | 调整 Android 打包配置 |
| `ci` | 持续集成流程调整 | 增加自动构建检查 |
| `chore` | 其他维护事项 | 更新开发工具配置 |
| `revert` | 撤销已有提交 | 回退技能结算改动 |

性能问题已登记为禅道 Bug 时，修复使用 `fix`，并填写 `Bug-Type: 性能`；主动优化使用 `perf`。美术、音效、数值配置修改按目的选择 `feat` 或 `fix`，不使用 `style`。

## 3. scope 规范

使用稳定的小写英文模块名，可用短横线连接，格式为 `[a-z][a-z0-9-]*`。团队统一维护可用列表，避免同一模块出现多个名称。

| scope | 范围 | scope | 范围 |
| --- | --- | --- | --- |
| `battle` | 战斗 | `skill` | 技能 |
| `ui` | 界面 | `bag` | 背包 |
| `resource` | 资源加载与管理 | `render` | 渲染与特效 |
| `network` | 网络通信 | `login` | 登录 |
| `audio` | 音效与音乐 | `config` | 数值与配置 |
| `server` | 服务端公共逻辑 | `build` | 构建与打包 |
| `tools` | 编辑器与开发工具 | `core` | 跨模块公共基础能力 |

优先选择主要受影响的模块，不在 scope 中堆叠多个名称。紧密关联的跨模块改动可在正文列明范围；无关改动拆分提交。

## 4. 关联与验证字段

| 字段 | 必填规则 | 格式与含义 |
| --- | --- | --- |
| `Zentao-Bug` | `fix` 必填；其他类型仅在实际关联 Bug 时填写 | 正整数编号，不加 `#`；如 `1352` |
| `Bug-Type` | 出现 `Zentao-Bug` 时必填 | 使用团队约定、与禅道一致的分类 |
| `Module` | `fix`、`feat`、`perf`、`refactor` 及其他关联 Bug 的提交必填 | 中文业务路径，如 `战斗/炮塔` |
| `Test` | 所有提交必填 | 实际验证环境、步骤及结果；未验证须写明原因 |

推荐 Bug 分类：`功能`、`表现`、`性能`、`崩溃`、`兼容性`、`网络`、`数值`、`资源`、`其他`。落地时以内部禅道实际分类为准，统一取值或映射；一个 Bug 填写一个主要分类。

`scope` 用于快速筛选技术模块，`Module` 用于定位业务范围。`Test` 不得仅写“已测试”或“正常”；不能验证时写 `未验证：原因；后续验证计划`，不得把预期结果写成已通过。纯文档改动可写 `不适用运行测试；已检查格式与示例一致性`。

## 5. Bug 修复示例

以下编号及验证记录仅作格式示例，提交时应替换为真实信息。

```text
fix(resource): 修复弱网下炮塔升级后贴图未刷新

升级完成时资源可能尚未加载，导致界面保留旧贴图。
资源加载完成后检查节点和当前等级，再刷新贴图。

Zentao-Bug: 1352
Bug-Type: 资源
Module: 战斗/炮塔
Test: Android 真机模拟弱网，连续升级炮塔 1 至 3 级，加载完成后贴图正确且无报错
```

## 6. 功能、性能与重构示例

### 新功能

```text
feat(bag): 新增道具批量出售功能

Module: 背包/道具出售
Test: 测试服分别出售单件、多件及锁定道具，收益正确，锁定道具不可出售
```

### 主动性能优化

```text
perf(battle): 复用伤害飘字节点以减少对象创建

Module: 战斗/伤害飘字
Test: 同一 Android 设备与 100 单位战斗场景下，预热后节点创建次数由每分钟 600 次降至 0 次，飘字显示正常
```

性能提交应记录设备、场景和可比较的实测指标，不填写未经测量的提升比例。

### 重构

```text
refactor(skill): 拆分技能目标筛选与伤害结算逻辑

Module: 战斗/技能
Test: 单体、群体及持续伤害用例通过，相同输入下目标列表和伤害结果与重构前一致
```

## 7. 多 Bug 规则

- 默认一个提交只修复一个 Bug；同一个 Bug 可对应多个提交，每个提交均保留完整关联字段。
- 仅当多个 Bug 根因相同、修复不可合理拆分，且 `Bug-Type`、`Module` 相同时，允许在同一提交关联多个编号。
- 编号使用英文逗号加空格分隔，去重并升序排列，如 `Zentao-Bug: 1352, 1388`；只写一行该字段。
- 正文说明每个编号对应的问题，`Test` 按编号记录各自验证结果；不同根因、分类或模块的 Bug 应拆分提交。
- Squash 合并时，最终提交消息必须保留全部关联编号和验证信息。

```text
fix(resource): 修复异步加载后战斗单位贴图未刷新

1352：炮塔升级后保留旧贴图。
1388：炮塔换皮后保留旧贴图。
两者均由资源加载完成后未刷新引起，统一修复加载回调。

Zentao-Bug: 1352, 1388
Bug-Type: 资源
Module: 战斗/炮塔
Test: Android 弱网；1352 连续升级后贴图正确；1388 连续换皮后贴图正确
```

## 8. 推荐简化版

日常提交优先省略可选正文，保留标题及必填字段；简化版不降低 Bug 关联要求。

```text
fix(ui): 修复背包关闭后遮罩未移除

Zentao-Bug: 1420
Bug-Type: 表现
Module: 背包/界面
Test: Android 真机连续打开并关闭背包 10 次，遮罩均移除，主界面可点击
```

非 Bug 提交省略 `Zentao-Bug` 和 `Bug-Type`，按字段规则填写，例如：

```text
docs(tools): 补充资源导入说明

Test: 不适用运行测试；已检查文档格式与操作步骤
```

## 9. 提交检查规则

可在提交钩子或 CI 中检查格式，并由审查人员核对内容。

- [ ] 标题符合 `<type>(<scope>): <中文简述>`，type 和 scope 在团队允许列表中。
- [ ] 一个提交对应一个明确目的，简述能说明具体变更。
- [ ] `fix` 包含 `Zentao-Bug`、`Bug-Type`、`Module`、`Test` 四个非空字段。
- [ ] 任意提交出现 `Zentao-Bug` 时，同样包含其余三个字段；未关联 Bug 时省略 `Bug-Type`。
- [ ] `feat`、`perf`、`refactor` 包含 `Module` 和 `Test`；其余提交至少包含 `Test`。
- [ ] 字段名大小写、顺序、分隔符一致；每个字段只出现一次。
- [ ] Bug 编号真实存在，分类和模块与禅道记录一致；多 Bug 符合第 7 节规则。
- [ ] 验证记录真实、具体；未验证已说明原因与计划，合并前按项目要求完成验证。
- [ ] `perf` 有可比较的验证依据；`refactor` 有行为保持一致的验证；`revert` 在正文注明原提交哈希和撤销原因。
- [ ] 最终合入的提交消息符合规范；自动生成的 Merge 提交可豁免格式检查，Squash 提交不可豁免。

格式检查不能证明 Bug 真实存在或测试已通过；这些内容需通过禅道查询和审查核实。
